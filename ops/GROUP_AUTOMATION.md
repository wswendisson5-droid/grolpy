# WAZZO group maintenance — 21 October 2026

This rollout is restricted in server/groupAutomation.ts by ownership of the existing campaign and its instance/phone binding to the requested account. It targets campaign div-1791448389589. Other users receive available:false and cannot enable it. No SSH credentials, keys or new external permissions are required by this feature.

A server timer checks once a minute. A durable per-account MySQL named lock prevents concurrent workers from joining in parallel; each completed pass schedules the next pass at least two minutes later. The existing Passenger scheduler wake/cron must remain enabled. The service does not depend on an open browser. It initializes only when a unique campaign owner, the existing campaign instance, expected phone suffix and active subscription match; the full phone is then bound privately in MySQL. It preserves message/image and history, changes that campaign to daily 07:00/15:00/21:00 in America/Sao_Paulo, and skips elapsed slots on first activation.

The automation reads all public paginated WAZZO catalog invitations, then validates the invitation through Evolution 2.3.7 inviteInfo. It rejects closed/unknown conversations, communities, incompatible names/descriptions, explicit advertising prohibitions, common once-a-day restrictions, undersized groups and approval-required invitations. Unknown metadata is rejected. Text matching is conservative and cannot interpret every possible custom rule; ambiguous purpose is excluded. Open existing memberships use the same criteria. Campaign selection contains at most 100 validated groups.

At most one invitation is accepted per pass. A durable intent is saved before accepting it; an ambiguous outcome is never blindly retried or counted. Membership must be rechecked against real participants after acceptance. Pending outcomes reserve capacity but are not counted as validated members. Removed/unavailable JIDs are excluded from re-entry, including through changed invite codes. Replacements are different groups. Failed/limited group snapshots cannot erase membership or trigger replacement bursts. Backoff is persisted, grows up to one hour, and survives process restarts. Candidate progress, logs and exclusions live in admin_state under group-automation:<user ID>.

Only the managed campaign gets dynamic destinations and per-recipient live eligibility checks. It must still pass existing active-subscription and instance checks, serialized delivery, and per-slot delivery claims. A live metadata rate limit stops the round rather than continuing to hit the upstream. No manual immediate dispatch is initiated by deployment. An empty managed selection waits for eligible groups instead of failing the schedule.

The authenticated Grupos WAZZO view exposes actual count, state, schedule, recent events, and pause/resume. Pausing stops membership maintenance and disables the managed campaign. Existing unrelated campaigns are unchanged. Existing jobs finish their current queued round before the pause control can change state. A changed instance/phone halts maintenance and per-recipient sends instead of following a different account.

Production verification must observe the authenticated status endpoint and campaign schedule after deployment. A live WhatsApp rate limit is a waiting state, never success. The current target is 100 groups, each with at least 100 participants. The initial audience must reach 100 before any managed dispatch is released. Readiness is persisted in the automation state, and the campaign mirrors it as groupAutomationReady. Reaching the threshold skips elapsed slots; it never triggers an immediate or catch-up send. Every scheduled round requires the complete target. If a fresh inventory drops the selection below 100, reconciliation persists the vacancies and blocks that dispatch; the worker refills the audience before the scheduler can release another round. Before each round, a successful complete membership inventory reconciles missing, closed and community groups; failed inventories abort sending without inventing removals. Every recipient is checked again immediately before sending. Confirmed invalid destinations free a slot under the same account lease, and cached inventories cannot reintroduce excluded destinations. Unknown API failures preserve membership and upstream cooldowns. Chip-warming/message-exchange audiences are excluded.

Catalog discovery version 2 does not use saved member counts, titles or descriptions as admission decisions. It requests the complete catalog and consults each previously unverified invitation; all minimum-size, subject, open-conversation, membership and community checks remain mandatory on live data before accepting or counting a group. Existing verified attempts and upstream cooldowns survive the migration. Still-blocked attempts are filtered before queuing, allowing pagination to move forward without spending another scan slot on them. Catalog visit totals, pass completion and the actual exhausted/waiting state are persisted and exposed in the panel. Exhaustion is not presented as a successful target or guaranteed future growth.

The existing scheduled /api/health wake also calls the enabled maintenance worker, preserving its lease and nextRunAt; collection no longer depends only on a Passenger process surviving long enough for setInterval. Health and authenticated status expose the running catalog engine version so file upload alone is not confused with an updated running process.

Strict full-audience dispatch: groupAutomationReady and readyForDispatch require 100 currently selected eligible groups, even after the initial threshold was reached. This is a selection requirement; individual upstream deliveries can still fail or become unavailable after preflight.
