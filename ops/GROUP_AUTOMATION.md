# WAZZO group maintenance — 16 October 2026

This rollout is restricted in server/groupAutomation.ts by ownership of the existing campaign and its instance/phone binding to the requested account. It targets campaign div-1791448389589. Other users receive available:false and cannot enable it. No SSH credentials, keys or new external permissions are required by this feature.

A server timer checks once a minute. A durable per-account MySQL named lock prevents concurrent workers from joining in parallel; each completed pass schedules the next pass at least two minutes later. The existing Passenger scheduler wake/cron must remain enabled. The service does not depend on an open browser. It initializes only when a unique campaign owner, the existing campaign instance, expected phone suffix and active subscription match; the full phone is then bound privately in MySQL. It preserves message/image and history, changes that campaign to daily 07:00/15:00/21:00 in America/Sao_Paulo, and skips elapsed slots on first activation.

The automation reads public paginated WAZZO catalog entries (minimum 100), then validates the invitation through Evolution 2.3.7 inviteInfo. It rejects closed/unknown conversations, communities, incompatible names/descriptions, explicit advertising prohibitions, common once-a-day restrictions, undersized groups and approval-required invitations. Unknown metadata is rejected. Text matching is conservative and cannot interpret every possible custom rule; ambiguous purpose is excluded. Open existing memberships use the same criteria. Campaign selection contains at most 100 validated groups.

At most one invitation is accepted per pass. A durable intent is saved before accepting it; an ambiguous outcome is never blindly retried or counted. Membership must be rechecked against real participants after acceptance. Pending outcomes reserve capacity but are not counted as validated members. Removed/unavailable JIDs are excluded from re-entry, including through changed invite codes. Replacements are different groups. Failed/limited group snapshots cannot erase membership or trigger replacement bursts. Backoff is persisted, grows up to one hour, and survives process restarts. Candidate progress, logs and exclusions live in admin_state under group-automation:<user ID>.

Only the managed campaign gets dynamic destinations and per-recipient live eligibility checks. It must still pass existing active-subscription and instance checks, serialized delivery, and per-slot delivery claims. A live metadata rate limit stops the round rather than continuing to hit the upstream. No manual immediate dispatch is initiated by deployment. An empty managed selection waits for eligible groups instead of failing the schedule.

The authenticated Grupos WAZZO view exposes actual count, state, schedule, recent events, and pause/resume. Pausing stops membership maintenance and disables the managed campaign. Existing unrelated campaigns are unchanged. Existing jobs finish their current queued round before the pause control can change state. A changed instance/phone halts maintenance and per-recipient sends instead of following a different account.

Validation: node --import tsx --test server/groupAutomation.test.ts; npm run lint; npm run build. The deterministic tests use mock upstream/DB adapters and are not proof of 100 real memberships or future delivery. Production verification must observe the authenticated status endpoint and campaign schedule after deployment. A live WhatsApp rate limit is a waiting state, never success. Do not claim the target is reached before the status count actually shows 100.
